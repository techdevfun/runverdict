# runverdict

Measure **your app** across the JavaScript runtimes installed on **your machine**
and get an upgrade verdict with reasons - not a headline benchmark measured
on someone else's app on someone else's machine.

## Problem

Node 26 entered Active LTS on 2026-10-28. Teams on Node 20 and older run a
runtime with no security fixes. Teams on Node 22 and 24 must plan a move.
Teams choosing between Node and Bun have only headline benchmarks. Nobody's
tool answers, for your app on your machine: does it load on the target
runtime, how fast is it there, and should you upgrade - with reasons, not a
headline.

## Solution

`runverdict` is a local, zero-dependency TypeScript CLI. No account, no
network beyond localhost, no downloads, no data leaves the machine. It never
downloads a runtime: it measures only runtimes already installed and reports
the rest as not-installed.

For each runtime it reports:

- Version and EOL status from a built-in schedule table (Node only; see below).
- A load check: the entry is spawned and a failure records the stderr tail
  verbatim, which is what names a broken native addon or a missing module.
- Startup timing: median of 5 spawns, spawn to first stdout line.
- An HTTP workload with the built-in `http` client only: requests/second,
  p50/p95 latency, and peak RSS, using the same workload, in the same order,
  on the same machine for every runtime.

Then it returns a deterministic verdict:

| Verdict | Rule |
| --- | --- |
| `BLOCKED` | The target runtime fails the load check, or no runtime produced a measurement. Reasons name the failing runtime and its stderr tail. Exit code 1. |
| `UPGRADE-READY` | The current runtime is EOL or Maintenance, the target runtime loads, and its req/s is not worse than the current runtime's by more than 10%. Exit code 0. |
| `STAY` | Otherwise, with reasons and numbers. A measured regression beyond 10% is a reason to stay, stated with both numbers. Exit code 0. |

Definitions: the current runtime is the first runtime in `--runtimes` order
with a measurement; the target is the best-performing other measured runtime,
if any. With a single measured runtime there is no target to compare against,
so the verdict is `STAY`.

### Built-in Node EOL schedule

| Node major | Status | EOL |
| --- | --- | --- |
| 20 | EOL | 2026-04-30 |
| 22 | Maintenance | 2027-04-30 |
| 24 | Maintenance | 2028-04-30 |
| 26 | Active LTS | 2029-04-30 |

An unknown Node major is reported as `UNKNOWN`, never guessed. Bun has no
LTS/EOL schedule: runverdict reports the Bun version only and never invents
an EOL date for Bun. Deno is explicitly out of scope in v1: it is not
detected, and passing `--runtimes deno` is an error, not a silent omission.

## Install in 3 steps

Requires Node >= 20.

```sh
git clone https://github.com/techdevfun/runverdict
cd runverdict
npm install
```

Then link the binary once for local use:

```sh
npm link
```

## Runnable example

The repository ships a zero-dependency sample app with `/health` and `/json`
endpoints (`examples/sample-app.js`). It listens on `process.env.PORT`.

```sh
runverdict runtimes
runverdict measure --entry examples/sample-app.js --url /json --runtimes node,bun --duration 5 --connections 20 --json out.json
runverdict --version
```

`--duration` defaults to 10 seconds and `--connections` defaults to 20.
The JSON manifest carries runtime versions, EOL statuses, every measured
number, run counts, the verdict with reasons, and the machine note:
"single-machine measurement, not a general claim".

Exit codes: 0 when the verdict is `UPGRADE-READY` or `STAY`; 1 when the
verdict is `BLOCKED` or when no usable runtime measurement exists; 2 for a
usage error.

## Honest limits

- It does not profile. For flame graphs and event-loop diagnosis,
  clinic.js beats us. It does not do statistical outlier modeling; hyperfine
  beats us. It does not offer HTTP load options; autocannon beats us.
  This tool does the upgrade decision, which none of them do.
- A load check proves the entry loads, not full compatibility. A passing
  load check is not a guarantee the app behaves identically on another runtime.
- Numbers are this machine's. A faster runtime here is not a claim about any
  other machine, app, or workload.
- It never downloads runtimes, never touches the network beyond localhost,
  and never reads files outside the app directory except the runtime binaries.

## Roadmap

- Additional report formats for the JSON manifest.
- A documented evaluation of a third runtime inventory entry, only if it can
  be measured with the same load, startup, and workload checks.
- Longer, configurable workload shapes, without changing the deterministic
  verdict rules.
